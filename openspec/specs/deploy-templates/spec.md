# deploy-templates Specification

## Purpose
Installs a deployment workflow for web projects on the platform the project uses, mapped to the long-lived branches of its preset, with approval before production and a way back to the previous version.

## Requirements

### Requirement: Platform selection
The configuration key `deploy.platform` SHALL accept `none` (default), `vercel`, `cloudflare` and `docker`. `init` SHALL install the deployment template of the chosen platform and SHALL install none for `none`. It MUST NOT overwrite a deployment workflow the project already has.

#### Scenario: No platform
- **WHEN** `deploy.platform` is not set
- **THEN** `init` installs no deployment workflow

#### Scenario: Existing workflow
- **WHEN** `.github/workflows/deploy.yml` already exists and was not generated by the plugin
- **THEN** `init` leaves it unchanged and says it was skipped

### Requirement: Branches map to environments
The installed deployment SHALL deploy each long-lived branch to one environment: in `standard`, the working branch to `staging` and the release branch to `production`; in `environments`, the working branch to `development`, the staging branch to `staging` and the release branch to `production`; in `trunk`, the release branch to `production`.

#### Scenario: Standard
- **WHEN** the preset is `standard` and a commit lands on `develop`
- **THEN** the workflow deploys to the `staging` environment

#### Scenario: Environments
- **WHEN** the preset is `environments` and a commit lands on `staging`
- **THEN** the workflow deploys to the `staging` environment

### Requirement: Production needs approval
Deployments to `production` SHALL run in a GitHub environment named `production`, and the setup instructions SHALL tell the user to add required reviewers to it. `doctor` SHALL warn when a deployment platform is configured and the `production` environment has no required reviewer.

#### Scenario: No reviewer
- **WHEN** `deploy.platform` is `docker` and the `production` environment has no required reviewers
- **THEN** `doctor` reports a warning with the settings page to open

### Requirement: Docker deployment builds once
For `docker`, the workflow SHALL build the image once per source tree, push it to the GitHub container registry, and deploy that image over SSH with Docker Compose. When an image for the same source tree already exists, the workflow SHALL deploy it without building again, so the image tested on a lower environment is the one that reaches production.

#### Scenario: Promotion without changes
- **WHEN** the source tree merged into `main` is identical to the one already built on `develop`
- **THEN** production deploys the existing image and no build runs

#### Scenario: Missing secrets
- **WHEN** the deployment secrets of an environment are not set
- **THEN** the job fails with a message naming the missing secrets

### Requirement: Cloudflare deployment
For `cloudflare`, the workflow SHALL deploy with Wrangler to the Wrangler environment that matches the branch, using a Cloudflare API token and account id read from the secrets of the GitHub environment.

#### Scenario: Staging
- **WHEN** a commit lands on the branch mapped to `staging`
- **THEN** the workflow deploys with the Wrangler environment `staging`

### Requirement: Vercel uses its Git integration
For `vercel`, `init` SHALL install no deployment workflow and SHALL write into `CONTRIBUTING.md` the Vercel project settings the preset needs: the production branch and the domain to assign to each other long-lived branch.

#### Scenario: Standard on Vercel
- **WHEN** `deploy.platform` is `vercel` and the preset is `standard`
- **THEN** no deployment workflow is installed and the deployment section names `main` as the production branch and `develop` as the staging branch

### Requirement: Rollback
The Docker and Cloudflare workflows SHALL accept a manual run that takes an environment and a released version and deploys that version again.

#### Scenario: Back to the previous version
- **WHEN** a maintainer runs the workflow manually with environment `production` and version `v1.3.0`
- **THEN** the build of `v1.3.0` is deployed to production after the environment's approval

### Requirement: Secrets are named, never written
The templates SHALL refer to secrets by name only. `init` SHALL list the secret names to create for the chosen platform and MUST NOT ask for, print or store their values.

#### Scenario: Docker secrets
- **WHEN** `init` installs the Docker template
- **THEN** it lists the secret names each environment needs and writes no value anywhere
