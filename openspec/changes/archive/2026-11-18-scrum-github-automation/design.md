# Design

## Context

Động cơ và phạm vi: xem `proposal.md`. Yêu cầu hành vi: xem `specs/`.

Hiện trạng và ràng buộc:

- Repo này mới chỉ có OpenSpec (`openspec/`, `.claude/commands/opsx`, `.claude/skills/openspec-*`), chưa có mã, chưa có remote GitHub.
- Lõi chọn Bash + `gh` + `jq` + `yq` (mikefarah v4). Máy dev là macOS: Bash mặc định 3.2 (không có associative array, `mapfile`), `date` BSD khác GNU. Runner `ubuntu-latest` có sẵn `gh`, `jq`, `yq`.
- Máy dev hiện chưa có `yq`, `bats`, `shellcheck`. Token `gh` đang hết hạn.
- Sandbox của Claude Code chặn shell ghi vào `.claude/skills`, và chặn mạng tới `api.github.com` trừ khi lệnh khai báo domain này.
- GitHub Actions: sự kiện do `GITHUB_TOKEN` gây ra không kích hoạt workflow khác; token của PR từ fork chỉ có quyền đọc khi dùng trigger `pull_request`.

## Goals / Non-Goals

**Goals:**

- Mọi logic tính toán (gộp cấu hình, kế hoạch label, nhận diện liên kết, đổi trạng thái, velocity, burndown, digest) là hàm thuần trên JSON, test được offline bằng fixture.
- Một lõi duy nhất, gọi từ skill của Claude, từ workflow Actions, và từ dòng lệnh.
- Không có thao tác ghi nào lên GitHub mà người dùng không thấy trước (với lệnh tương tác) hoặc không lường trước được (với workflow).

**Non-Goals:**

- Gỡ cài đặt tự động (xoá label, xoá file `.github/`).
- Lưu lịch sử điểm khi điểm của task đổi giữa sprint; burndown dùng điểm hiện tại.
- Hỗ trợ GitHub Enterprise Server, Projects v2, hay chạy trên Windows ngoài WSL.

## Decisions

### 1. Bố cục plugin

```
.claude-plugin/marketplace.json          # marketplace cục bộ, trỏ tới plugins/scrum-github
plugins/scrum-github/
  .claude-plugin/plugin.json
  skills/<lệnh>/SKILL.md                 # scrum-init, sprint-new, sprint-plan, task-new,
                                         # task-start, sprint-status, sprint-report, sprint-close
  runtime/                               # phần được vendor vào repo đích
    bin/scrum                            # dispatcher: scrum <lệnh> [tuỳ chọn]
    lib/*.sh                             # config, gh wrapper, từng lệnh
    lib/jq/*.jq                          # hàm thuần
  templates/                             # scrum.yml, ISSUE_TEMPLATE, PR template, workflows, report.html
  tests/run.sh, tests/test_*.sh, tests/fixtures/
  README.md
```

Skill chỉ mô tả cách gọi `${CLAUDE_PLUGIN_ROOT}/runtime/bin/scrum` và cách trình bày kết quả; không chứa logic. Riêng `sprint-plan` chứa hướng dẫn cho Claude soạn đề xuất task.

Lý do đặt ngoài `.claude/`: cài được vào nhiều repo, và sandbox không chặn ghi vào `plugins/`. Phương án bỏ qua: skill cục bộ trong `.claude/skills` (chỉ dùng được ở repo này).

Tên lệnh: skill của plugin có namespace, nên người dùng gõ `/scrum-github:sprint-new`. Spec viết tắt là `/sprint-new`. README ghi rõ cả hai.

### 2. Vendor runtime vào repo đích

`scrum-init` chép `runtime/` vào `.github/scrum/` của repo đích. Workflow gọi `.github/scrum/bin/scrum`. Thư mục này thuộc quyền plugin: mỗi lần `scrum-init` ghi đè toàn bộ, file đầu có dòng "generated by scrum-github vX.Y.Z, do not edit". Các template người dùng có thể sửa (PR template, Issue Form, workflow) theo quy tắc xung đột trong spec `repo-bootstrap`.

Phương án bỏ qua: workflow tải script từ repo plugin lúc chạy. Bị loại vì phụ thuộc mạng và repo plugin phải public, khó khoá phiên bản.

### 3. Cấu hình: YAML đọc bằng yq, xử lý bằng jq

`config.sh` chạy `yq -o=json` để chuyển `.github/scrum.yml` sang JSON, rồi `jq` gộp với mặc định (`templates/defaults.json`) và kiểm tra hợp lệ. Mọi phần sau chỉ nhận JSON đã gộp. Kiểm tra `yq --version` có chữ `mikefarah` để tránh nhầm bản `yq` viết bằng Python.

Dạng cấu hình (mặc định):

```yaml
version: 1
timezone: UTC
sprint: { length_days: 5, name_pattern: "Sprint {n}" }
points: { scale: [0, 1, 3, 7], label_prefix: "points: " }
statuses: { label_prefix: "status: ", new: "New", in_progress: "In progress", done: "Done" }
labels: { bug: "bug", feature: "type: feature", meta: "scrum: meta", no_task: "no-task" }
branch: { pattern: "feat/{number}-{slug}" }
digest: { enabled: true, cron: "0 1 * * 1-5" }
```

### 4. Hàm thuần bằng jq, lời gọi GitHub tách riêng

Mỗi lệnh có ba bước: (1) `gh api` lấy JSON thô, (2) một file `.jq` tính kế hoạch hoặc kết quả, (3) áp kế hoạch bằng `gh api`. Bước 2 không chạm mạng, test bằng `jq -f x.jq fixture.json` so với kết quả mong đợi.

Tính ngày cũng làm trong jq (`strptime`, `mktime`, `strftime`), không dùng `date`, để tránh khác biệt giữa BSD và GNU. Múi giờ: chuyển timestamp sang ngày theo độ lệch của `timezone` lấy một lần bằng `TZ=<tz> date +%z` lúc chạy, rồi truyền vào jq.

Phương án bỏ qua: logic viết bằng Bash. Bash 3.2 không có cấu trúc dữ liệu đủ dùng và khó test.

### 5. Lưu thông tin sprint trong mô tả milestone

Milestone của GitHub chỉ có `due_on` (và giờ của nó lệch theo múi giờ). Ngày bắt đầu, ngày kết thúc và velocity ghi thành marker trong mô tả:

```
<!-- scrum:start=2014-09-22 end=2014-09-26 -->
<!-- scrum:velocity=11 -->
```

Marker là nguồn sự thật; `due_on` chỉ để hiển thị trên giao diện GitHub. Milestone không có marker (tạo bằng tay) được coi là sprint bắt đầu từ `created_at` và kết thúc ở `due_on`.

### 6. Lấy dữ liệu task

`gh api --paginate "repos/{o}/{r}/issues?milestone=<n>&state=all&per_page=100"` trả cả issue và PR; jq loại phần tử có khoá `pull_request`, issue có label feature hoặc meta. `state_reason` (`completed`, `not_planned`) quyết định task có tính vào velocity hay không; `closed_at` dùng cho burndown.

### 7. Workflow

| Workflow | Trigger | Việc |
|---|---|---|
| `scrum-status-sync.yml` | `pull_request_target` (opened, reopened, ready_for_review, edited, closed); `issues` (closed, reopened) | Đổi trạng thái theo spec `pr-task-linking` |
| `scrum-pr-link-check.yml` | `pull_request_target` (opened, edited, reopened, labeled, unlabeled, ready_for_review, synchronize) | Job thất bại khi PR thiếu liên kết |
| `scrum-daily-digest.yml` | `schedule` (cron lấy từ cấu hình lúc init), `workflow_dispatch` | Đăng digest |

Dùng `pull_request_target` để PR từ fork vẫn có token ghi issue. Workflow chỉ checkout branch gốc (để lấy `.github/scrum/`), không bao giờ checkout code của PR, và đọc mô tả PR qua `jq` từ `$GITHUB_EVENT_PATH`, không nội suy vào lệnh shell. Quyền khai báo `issues: write, pull-requests: read, contents: read`.

Việc đổi nhãn bằng `GITHUB_TOKEN` không kích hoạt lại workflow, nên không có vòng lặp. Khi PR merge, cả sự kiện `pull_request_target.closed` lẫn `issues.closed` (do GitHub tự đóng theo keyword) đều có thể chạy; thao tác đặt trạng thái là idempotent nên chạy hai lần cho cùng kết quả.

Cron của digest cố định trong file workflow, nên đổi `digest.cron` cần chạy lại `scrum-init` với tuỳ chọn ghi đè workflow. `digest.enabled` được đọc lúc chạy.

### 8. Đặt trạng thái

Một hàm `set_status <issue> <status>` lấy label hiện tại, tính tập label mới bằng jq (gỡ mọi label có tiền tố trạng thái, thêm label đích), và gọi `PUT /issues/{n}/labels` một lần khi tập label thay đổi. Gọi một lần thay vì gỡ rồi thêm để không có lúc task mất trạng thái.

### 9. AI lập kế hoạch

Skill `sprint-plan` hướng dẫn Claude: đọc cấu hình (thang điểm), soạn danh sách task dạng JSON theo schema `templates/plan.schema.json`, trình bày thành bảng, sửa theo phản hồi, và chỉ khi người dùng duyệt mới gọi `scrum plan apply <file>`. Lệnh `plan apply` kiểm tra lại điểm, tạo issue feature, tạo task, gắn sub-issue qua `POST /issues/{n}/sub_issues` (dùng `id` của issue con, không phải số issue); nếu bị từ chối thì ghi danh sách checkbox vào issue feature.

### 10. Báo cáo HTML

`templates/report.html` là trang tĩnh có chỗ chèn một khối `<script type="application/json">`. `scrum report` tính dữ liệu bằng jq rồi thay chỗ chèn. Biểu đồ vẽ bằng SVG từ JS inline, không thư viện ngoài, để file mở được khi không có mạng. Dữ liệu chèn vào được escape `</` để không đóng thẻ script sớm.

### 11. Kiểm thử

Không thêm `bats`. `tests/run.sh` là bộ chạy Bash nhỏ có `assert_eq` và `assert_json_eq` (so sánh qua `jq -S`). Ba tầng:

1. Hàm jq: fixture JSON vào, JSON mong đợi ra.
2. Lệnh: chạy `scrum` với biến môi trường `SCRUM_GH` trỏ tới một `gh` giả ghi lại lời gọi và trả fixture; kiểm tra danh sách lời gọi.
3. End-to-end: kịch bản tay trên repo sandbox, ghi trong README.

Chạy `shellcheck` nếu máy có, không bắt buộc.

## Risks / Trade-offs

- [Burndown sai khi task thêm vào giữa sprint hoặc đổi điểm] → Ghi giới hạn trong báo cáo; dùng điểm hiện tại và coi mọi task có từ ngày đầu. Có thể đọc timeline event ở phiên bản sau.
- [`pull_request_target` có token ghi khi PR từ fork] → Không checkout code PR, không chạy gì từ PR, coi mô tả PR là dữ liệu.
- [Nhầm bản `yq`] → Kiểm tra chuỗi phiên bản, báo cách cài đúng bản.
- [Rate limit API ở repo lớn] → Mỗi lệnh lấy dữ liệu theo milestone, phân trang 100; digest chạy một lần mỗi ngày.
- [Runtime vendor lệch phiên bản giữa các repo] → Ghi phiên bản trong header file; `scrum-init` in phiên bản cũ và mới khi cập nhật.
- [Người dùng sửa label bằng tay gây nhiều trạng thái] → Mọi thao tác đặt trạng thái chuẩn hoá về đúng một label.
- [Sandbox của Claude chặn mạng tới GitHub] → Skill khai báo `api.github.com` khi gọi `gh`; người dùng có thể chỉnh bằng `/sandbox`.

## Migration Plan

Không có dữ liệu cũ cần chuyển. Cài đặt: thêm marketplace cục bộ (`/plugin marketplace add ./`), cài plugin, chạy `/scrum-github:scrum-init` trong repo đích, commit và push `.github/`. Gỡ: xoá các file `.github/scrum*` và workflow, gỡ plugin; label và milestone giữ nguyên.

## Open Questions

- Tên và owner của repo sandbox (người dùng tự tạo, hoặc cho phép `gh repo create` khi chạy end-to-end). Không ảnh hưởng thiết kế.
- Màu cụ thể cho từng label. Mặc định nằm trong `templates/defaults.json`, người dùng ghi đè qua khoá `colors` (tên label → mã màu) trong `scrum.yml`.
